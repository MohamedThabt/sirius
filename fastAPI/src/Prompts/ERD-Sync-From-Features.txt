# TASK:
Intelligently merge multiple feature-level ERDs into a cohesive module-level ERD while preserving manual customizations from the current module ERD. Your goal is to create a unified, consistent database schema that:
- Consolidates duplicate entities across features
- Resolves relationship conflicts
- Maintains referential integrity
- Preserves user's manual refinements where they don't conflict with features

# INSTRUCTIONS:

1. Entity Consolidation:
   - Identify entities that appear across multiple feature ERDs
   - Merge duplicate entities into single definitions
   - Combine all columns from duplicate entities (avoiding true duplicates)
   - If current module ERD has manual customizations (indexes, constraints, custom columns), preserve them unless they conflict with feature requirements

2. Relationship Resolution:
   - Identify all relationships across feature ERDs
   - Resolve conflicting cardinalities by choosing the most restrictive valid option
   - Ensure all FK relationships reference valid parent tables
   - Maintain referential integrity across the entire module

3. Column Consolidation Rules:
   - When merging duplicate columns, preserve the most restrictive constraints
   - If column types differ, use the more specific type (e.g., varchar(100) vs text → varchar(100))
   - Preserve manual indexes and comments from current module ERD
   - Add columns that exist in features but not in current ERD

4. Naming Consistency:
   - Standardize entity names (if some features use "User" and others use "Users", choose plural)
   - Ensure FK naming follows convention: <singular_table>_id
   - Tables: lowercase, plural, snake_case (orders, user_profiles)
   - Columns: snake_case (created_at, total_amount)

5. Column Definition Format (CRITICAL):
   - Every column must follow **exactly this format**:
       <type> <column_name> "<constraints>"
   - Constraints must be inside **ONE** set of quotes only
   - Valid constraints: PK, FK, UNIQUE, NOT NULL, ref:Table.column
   - Example:
       integer user_id "FK, NOT NULL, ref:users.id"
   - Forbidden:
       • NOT NULL alone without column
       • Multiple quotes like "FK" "ref:users.id"
       • Empty constraint lines

6. Relationship Rules:
   - Every FK MUST have a relationship line
   - Relationships must use this **exact syntax**:
       ChildTable }}o--|| ParentTable : "fk_column to pk_column"
   - fk_column must exist in the child table
   - pk_column must exist in the parent table
   - Self-relations must be declared only once (NO recursion)

7. Relationship Cardinalities Reference:
   - ||--|| : one-to-one (mandatory on both sides)
   - ||--o| : one-to-one (optional on right side)
   - ||--o{{ : one-to-many
   - }}o--|| : many-to-one
   - }}o--o{{ : many-to-many (requires junction table)

8. Preserve Manual Customizations:
   - Keep custom indexes from current module ERD (marked with -- INDEX comments)
   - Preserve custom constraints that don't conflict with features
   - Keep audit columns (created_by, updated_by, deleted_at) if present in current ERD
   - Maintain denormalization justifications as Mermaid comments

9. Handle Missing Entities:
   - If current module ERD has entities NOT in any feature ERD, keep them (they may be manually added infrastructure tables)
   - If feature ERDs reference external entities (from other modules), keep those FK references with comments

10. Conflict Resolution Strategy:
    - When features have conflicting constraints: choose the most restrictive (e.g., NOT NULL over nullable)
    - When features have conflicting types: choose the most specific (e.g., varchar(50) over text)
    - When relationships conflict: analyze the domain and choose the semantically correct cardinality
    - Document unresolvable conflicts as comments for manual review

11. Data Types:
    Use standard SQL types: integer, bigint, varchar, text, decimal, boolean, timestamp, date, json

12. Table Validity Rules:
    - No repeated NOT NULL
    - No repeated constraints
    - No empty lines with constraints only
    - No constraint or keyword written without a column

# MERGE STRATEGY:

1. Start with Current Module ERD as Base:
   - If current module ERD exists and is not empty, use it as the foundation
   - If current module ERD is empty, start fresh from feature ERDs

2. Process Each Feature ERD:
   - For each entity in feature ERD:
     • If entity exists in base: merge columns and relationships
     • If entity is new: add it to base
   - For each relationship in feature ERD:
     • If relationship exists: validate consistency
     • If relationship is new: add it to base

3. Validation Pass:
   - Ensure all FK references point to existing tables
   - Ensure all relationship lines reference existing FK columns
   - Check for orphaned tables (tables with no relationships)
   - Validate constraint syntax

4. Optimization Pass:
   - Remove true duplicate columns (same name, type, and constraints)
   - Consolidate redundant relationships
   - Add missing indexes for performance (FK columns, frequently queried fields)
