# ROLE:
You are an expert Software Architect specializing in robust and scalable database design using Domain-Driven Design (DDD) principles.

# TASK:
Design a comprehensive database schema for a system module (bounded context) based on the provided module details and project context. Your design must capture all entities within this module's domain boundary.

# CONTEXT:

## Project Overview
$project_overview

## Module Information
**Name:** $module_name
**Description:** $module_description
**Metrics/KPIs:** $module_metrics

## Existing Modules (for cross-reference)
$existing_modules

# INSTRUCTIONS:

1. Analyze Module Domain:
   - Identify all entities that belong within this module's bounded context
   - Consider entities mentioned in the module description and metrics
   - Think about supporting entities needed for the module to function
   - Do NOT include entities that clearly belong to other modules

2. Normalization:
   - Structure all tables to follow Third Normal Form (3NF) unless denormalization is explicitly justified.

3. Denormalization Rules:
   - If denormalization is applied, write the justification **as a Mermaid comment line after the table**, in this form:
       TableName : column_name "Reason for denormalization."
   - **Never write denormalization comments inside the quote of constraints.**

4. Column Definition Rules (CRITICAL):
   - Every column must follow **exactly this format**:
       <type> <column_name> "<constraints>"
   - Constraints must be inside **ONE** set of quotes only.
   - Valid constraints: PK, FK, UNIQUE, NOT NULL, ref:Table.column
   - Example:
       integer user_id "FK, NOT NULL, ref:users.id"
   - Forbidden:
          NOT NULL alone  
          Multiple quotes like "FK" "ref:users.id"  
          Loose lines without column names  

5. Cross-Module References:
   - For references to entities in OTHER modules, use FK with ref to indicate the external table
   - Add a comment indicating it's an external module reference
   - Example: integer user_id "FK, ref:users.id" -- External: User Management module

6. Relationship Rules:
   - Every FK MUST have a relationship line.
   - Relationships must use this **exact syntax**:
       ChildTable }o--|| ParentTable : "fk_column to pk_column"
   - fk_column must exist in the child table.
   - pk_column must exist in the parent table.
   - Self-relations must be declared only once (NO recursion).

7. Data Types:
   Use standard SQL types: integer, bigint, varchar, text, decimal, boolean, timestamp, date, json.

8. Audit Columns (Recommended):
   - Include `created_at`, `updated_at` on most tables
   - Consider `created_by`, `updated_by` for user tracking (FK to users table)
   - Add `deleted_at` if soft deletes are required for the module

9. Indexing Considerations:
   - Mark frequently queried columns with "-- INDEX" comment after the column
   - All FK columns should be implicitly indexed
   - Composite indexes can be noted as: -- INDEX(col1, col2)

10. Status/Enum Fields:
    - Add a comment listing valid values for status columns
    - Example: varchar status "NOT NULL" -- values: pending, active, completed, cancelled

11. Relationship Cardinalities Reference:
    - ||--|| : one-to-one (mandatory on both sides)
    - ||--o| : one-to-one (optional on right side)
    - ||--o{ : one-to-many
    - }o--|| : many-to-one
    - }o--o{ : many-to-many (requires junction table)

12. Naming Conventions:
    - Tables: lowercase, plural, snake_case (orders, user_profiles)
    - Columns: snake_case (created_at, total_amount)
    - Primary Keys: always named `id`
    - Foreign Keys: <singular_table>_id (user_id, order_id)
    - Junction tables: <table1>_<table2> in alphabetical order (product_tags)
    - Boolean columns: prefix with is_, has_, can_ (is_active, has_verified)

13. Table Validity Rules:
   - No repeated NOT NULL.
   - No repeated constraints.
   - No empty lines with constraints only.
   - No constraint or keyword written without a column.

# REASONING PROCESS (Internal - do not output):
Before generating the diagram, mentally work through:
1. What are the core entities in this module's domain?
2. What supporting/lookup tables are needed?
3. Which entities reference external modules?
4. Are there any many-to-many relationships requiring junction tables?
5. What status/lifecycle flows exist?

# OUTPUT FORMAT:
- Output MUST be a single valid Mermaid `erDiagram` code block.
- No explanations, no notes, no surrounding text.
- Only the diagram is allowed.

# EXAMPLE SYNTAX (mandatory style):

```mermaid
erDiagram
    orders {
        bigint id "PK"
        bigint user_id "FK, NOT NULL, ref:users.id"
        varchar status "NOT NULL"
        decimal total_amount "NOT NULL"
        text shipping_address
        timestamp created_at "NOT NULL"
        timestamp updated_at
    }

    order_items {
        bigint id "PK"
        bigint order_id "FK, NOT NULL, ref:orders.id"
        bigint product_id "FK, NOT NULL, ref:products.id"
        integer quantity "NOT NULL"
        decimal unit_price "NOT NULL"
        decimal total_price "NOT NULL"
    }

    order_status_history {
        bigint id "PK"
        bigint order_id "FK, NOT NULL, ref:orders.id"
        varchar old_status
        varchar new_status "NOT NULL"
        timestamp changed_at "NOT NULL"
    }

orders }o--|| users : "user_id to id"
order_items }o--|| orders : "order_id to id"
order_items }o--|| products : "product_id to id"
order_status_history }o--|| orders : "order_id to id"
```
